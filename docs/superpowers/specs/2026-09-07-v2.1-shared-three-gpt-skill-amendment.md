# v2.1 设计补丁：三套 GPT 共用同一 Skill，并共同维护

## 1. 修正原因

此前 v2.1 设计默认存在一个主要 GPT Orchestrator，再向 FYQ、XXT、CYQ 分发任务。该假设不完整。

实际使用方式是：

- FYQ 有自己的 GPT；
- XXT 有自己的 GPT；
- CYQ 有自己的 GPT；
- 三套 GPT 都会加载同一个 `cumcm-rigorous-workflow` Skill；
- 三个人都会持续整理、修改和扩充这个 Skill；
- GitHub 仓库是三方共享的唯一正式源。

因此 Runtime Skill 必须同时包含三套角色配置，并提供稳定的角色路由和多人维护规则。

本补丁覆盖原设计中任何“只有一个 GPT 实例消费 Skill”的隐含假设。

---

## 2. 新总体架构

```text
                         GitHub Repo
                    Single Source of Truth
                              │
             ┌────────────────┴────────────────┐
             │                                 │
      Shared Runtime Lite Skill          External Knowledge / Archive
             │
     ┌───────┼────────┐
     │       │        │
 FYQ GPT   XXT GPT   CYQ GPT
     │       │        │
     │       │        │
 Technical  Math     Paper
 + Orchestrator      Lead
     │       │        │
     └───────┴────────┘
             │
      shared project_state
      interfaces / handoffs
      frozen evidence
```

关键原则：

1. 三套 GPT 读取同一个 Shared Core；
2. 三套 GPT 只额外加载自己的 Role Profile；
3. 三套 GPT 都可以读取其他 Profile，用于理解接口和审查边界；
4. 三套 GPT 都可以通过 branch + PR 修改仓库；
5. 不允许每个人维护一个长期分叉的 Skill ZIP；
6. Runtime Skill 是一个包，内部包含三个 Profile。

## 3. Skill 分层

建议 Runtime Lite 采用：

```text
skills/cumcm-rigorous-workflow/
├── SKILL.md
├── core/
│   ├── authority.md
│   ├── evidence-chain.md
│   ├── freeze.md
│   ├── model-gates.md
│   ├── paper-gates.md
│   └── collaboration.md
├── profiles/
│   ├── FYQ_TECHNICAL_ORCHESTRATOR.md
│   ├── XXT_MATHEMATICAL.md
│   └── CYQ_PAPER.md
├── workflows/
│   ├── problem-intake.md
│   ├── modeling.md
│   ├── coding.md
│   ├── validation.md
│   ├── paper-handoff.md
│   └── submission.md
├── templates/
├── references/
├── tests/
└── manifest.yaml
```

### 3.1 Shared Core

所有 GPT 强制执行，Profile 不得覆盖：

- 官方规则与题面 authority；
- Source of Truth；
- Freeze；
- Interface First；
- evidence before claims；
- 数据审计与 leakage；
- model evidence Gate；
- robustness / sensitivity；
- paper evidence Gate；
- AI 使用记录真实性；
- 禁止编造结果；
- 禁止修改无关 frozen 内容。

### 3.2 Role Profile

Profile 负责同一规则下的不同默认行为和交付格式。

#### FYQ GPT：Technical + Orchestrator

默认职责：

- 全局 Question Map 与 Roadmap；
- 学术原型检索与路线裁决；
- FYQ / XXT 技术数学任务拆分；
- Codex Task；
- 数据、代码、接口、版本、Freeze；
- 三层 Review；
- 缺失实验识别；
- 生成给 CYQ 的 Paper Handoff 初稿。

它拥有较强的跨问调度权限，但不能越过 Mathematical Review 或 Frozen Authority。

#### XXT GPT：Mathematical

默认职责：

- 题意数学化；
- 变量、目标、hard constraints；
- 数学原型与候选模型；
- 公式与推导；
- 数值合理性；
- validator specification；
- exact anchor / bound / optimization adequacy；
- 审核 FYQ/Codex 的实现是否保持数学口径。

它可以写代码任务和局部实现，但不默认接管全局版本与 Freeze。

#### CYQ GPT：Paper

默认职责：

- 从早期即维护论文结构；
- 消费 Paper Handoff / Figure Registry / Frozen Metrics；
- 形成问题分析、模型建立、问题求解、结果分析、稳健性和摘要初稿；
- 重点写清“为了什么、为什么这样做、有什么好处、证据如何支撑结论”；
- 负责本问专属伪代码/算法流程的论文呈现；
- 图表叙事、版面和引用；
- AI 使用说明。

若证据缺失，CYQ GPT 返回缺口清单，不从上下文猜数字或自行创造模型优势。

## 4. Role Binding

同一 Skill 必须知道当前是哪一套 GPT 在运行。

优先级：

1. 当前环境显式提供 `ACTIVE_ROLE`；
2. 当前比赛 `project_state.yaml` 的 agent binding；
3. 用户首次启动时声明；
4. 无法确定时，只询问一次角色，不猜。

推荐角色值：

```text
FYQ_TECHNICAL_ORCHESTRATOR
XXT_MATHEMATICAL
CYQ_PAPER
```

允许同时读取多个 Profile 做 Review，但输出时必须声明主 Profile。

### 4.1 本地绑定不进入 Git

如果平台允许本地配置，使用：

```text
.cumcm-agent.local.yaml
```

示例：

```yaml
active_role: FYQ_TECHNICAL_ORCHESTRATOR
human_owner: FYQ
```

该文件加入 `.gitignore`，避免三个人互相覆盖身份。

如果平台不支持本地文件，则各自 GPT 的 Project / Custom Instructions 只需保存一条简短绑定：

> 使用 cumcm-rigorous-workflow，ACTIVE_ROLE=CYQ_PAPER。

角色规则本身仍全部来自共享 Skill，不复制进三套长 Prompt。

## 5. 三套 GPT 之间的协作协议

### 5.1 共同事实源

三套 GPT 不通过“另一边聊天里说过”同步正式状态。

正式共享只通过：

- `project_state.yaml`；
- Task；
- Interface；
- Handoff；
- Frozen Source of Truth；
- Figure Registry；
- Git commit / PR。

聊天记录可以提供上下文，但不覆盖这些正式来源。

### 5.2 输出契约

FYQ GPT → XXT GPT：

- 数学问题清单；
- 实现中的公式映射；
- constraint audit；
- 候选结果与异常；
- 待数学裁决项。

XXT GPT → FYQ GPT：

- MODEL_SPEC；
- 目标/约束；
- 参数范围；
- validator specification；
- 模型选择规则；
- 数学 Review 结论。

FYQ / XXT GPT → CYQ GPT：

- Paper Handoff；
- Frozen Metrics；
- 伪代码/算法流程；
- Robustness Evidence；
- Figure Registry；
- 论文禁区。

CYQ GPT → FYQ / XXT GPT：

- 论文证据缺口；
- 需要补的图/表/实验；
- 表述中发现的口径冲突；
- 摘要需要的正式数字列表。

## 6. 多人共同维护 Skill

三个人均为 Skill contributor。

### 6.1 禁止长期个人分叉

禁止形成：

```text
FYQ_skill_final.zip
XXT_skill_final2.zip
CYQ_skill_newest.zip
```

最终正式源只认 GitHub main。

### 6.2 Branch 规范

推荐：

```text
fyq/<topic>
xxt/<topic>
cyq/<topic>
shared/<topic>
```

任何人都可以修改任何目录，但要遵守 Review Ownership。

### 6.3 Review Ownership

#### 修改 Shared Core

至少需要一名其他角色审核。

涉及以下内容时建议两类 Review 都到位：

- 数学 Gate：XXT review；
- Freeze / interface / code：FYQ review；
- Paper / AI disclosure / prose：CYQ review。

#### 修改 Profile

对应角色拥有内容主审权，但其他角色可以指出接口冲突。

#### 修改模板或跨角色 Handoff

至少由输出方和消费方各审一次。

例如：

- Paper Handoff：FYQ/XXT + CYQ；
- MODEL_SPEC：XXT + FYQ；
- Codex Task：FYQ + XXT（涉及数学公式时）。

### 6.4 每个 PR 必填

```text
Why
Changed Rules
Affected Profiles
Behavior Change
Backward Compatibility
Evidence / Source
Validation
Migration Notes
```

### 6.5 Rule ID

重要规则应逐步增加稳定 ID，避免三个人重复写同一要求。

示例：

```text
CORE-AUTH-001
CORE-FREEZE-002
MATH-OPT-004
PAPER-PROSE-003
AI-DISCLOSURE-002
```

后续修改同一规则时更新原 Rule，不重复追加近义条目。

---

## 7. 防止三方编辑冲突

### 7.1 小文件化

`SKILL.md` 只做 dispatcher，不承载全部知识。

把规则拆到 Core/Profile/Workflow，减少三个人同时修改一个大文件造成 merge conflict。

### 7.2 Canonical vs Experimental

正式规则：

```text
skills/.../core
skills/.../profiles
```

实验性提案先放：

```text
proposals/<author>/<topic>.md
```

通过 Review 后再进入 Core/Profile。

### 7.3 不允许聊天规则覆盖仓库

某一套 GPT 在聊天里提出新规则，可以作为 Proposal；未 merge 前不得对另外两套 GPT 宣称它已经成为团队正式规则。

---

## 8. Runtime Lite 与知识库

三套 GPT 共用一个轻量 Runtime Skill。

运行包只保存：

- dispatcher；
- Shared Core；
- 三个 Role Profile；
- workflow；
- templates；
- tests；
- references/index；
- provenance。

优秀论文全文、截图和大型 corpus 继续外置。

因此三个人加载同一 Skill 时不会重复携带几十 MB PDF，也不会因为某个人只需要论文线就得到另一份完全不同的 Skill。

---

## 9. 验收新增项

v2.1 implementation plan 必须新增以下验收：

1. 同一个 Runtime Skill 内存在 FYQ / XXT / CYQ 三个 Profile；
2. `SKILL.md` 可以按 ACTIVE_ROLE 路由；
3. 未绑定角色时不会错误默认 CYQ/FYQ/XXT；
4. Shared Core 对三个 Profile 均生效；
5. FYQ Profile 可以生成数学 Review 请求与 Paper Handoff；
6. XXT Profile 可以生成 MODEL_SPEC 和数学 Review；
7. CYQ Profile 在证据不足时拒绝写“可直接定稿”正文；
8. 三个 Profile 对同一个 `project_state.yaml` 使用相同正式事实；
9. `.cumcm-agent.local.yaml` 被 gitignore；
10. PR / contribution governance 文档存在；
11. Skill 更新不要求重新打包原始优秀论文 corpus；
12. 静态测试验证三 Profile 所需关键文件与 Rule 引用存在。

---

## 10. 与原 v2.1 规格的关系

原规格中的 GPT Orchestrator 继续保留，但具体绑定为 FYQ 的 GPT Profile 的一项职责，而非唯一能够运行工作流的 AI 实例。

三套 GPT 都是同一工作流的一等消费者和贡献者。

原有三条生产线、Owner 动态分配、Interface First、Freeze、Paper Handoff、模型证据 Gate、评委反馈 Gate、AI Use Ledger 和 Runtime Lite 策略全部保留。
