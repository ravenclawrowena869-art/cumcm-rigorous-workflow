# 独立验收协议

主作者不能只验收自己的代码。

## 独立验收至少包括

1. 从 README 开始运行；
2. 检查输入是否来自正确附件；
3. 检查关键公式；
4. 检查时间索引；
5. 检查硬约束；
6. 独立复算 2–3 个核心指标；若论文头条数字不超过 3 个，则优先全部复算；
7. 检查输出是否满足题目要求；
8. 检查图表读取的数据；
9. 检查随机种子与依赖；
10. 在干净目录解压复现。

## REDTEAM-ISOLATION-001：信息隔离式独立复算

对会直接支撑摘要、核心结论、主模型优越性、关键可行性或最终决策的数字，独立验收优先采用“红队信息隔离”模式，而不是让第二个 Agent 阅读主模型代码后给出意见。

### 红队默认允许读取

- 官方题面、规则和附件；
- Question Contract、变量/指标定义；
- 原始输入数据；
- 已冻结的合成/仿真输入；
- 结果声明：待复算数值、单位、样本范围、聚合方式和必要口径。

### 红队默认禁止读取

- 主求解代码；
- 主建模者的推导笔记和实现说明；
- 主结果目录中的中间计算结果；
- 会暗示预期结论的审稿答案、仲裁意见或“应该得到什么数字”的提示。

红队应从零建立自己的计算路径。不同方法族能够得到同一物理量/统计量时，优先采用不同方法族，以降低“沿着同一错误路径一起错”的风险。

如果由于模型结构、商业求解器、计算预算或题目性质，完全隔离复算客观不可行，验收报告必须说明：

1. 哪些信息不得不共享；
2. 独立性因此损失了什么；
3. 用什么替代验证补偿，例如独立 validator、exact anchor、守恒复算、small-scale truth、另一实现语言或人工公式复核。

不能把“另一个 Agent 看了一遍原代码”直接标记为独立复算。

## REDTEAM-DEFINITION-001：先同口径复算，再做独立口径挑战

为避免把“口径不同”误判成“数值算错”，核心指标建议分两层复算：

### A. 同声明口径复算

严格使用主结果声明中的：

- 数据范围；
- 单位；
- 异常值处理；
- 时间窗口；
- 聚合方式；
- 公式定义。

这一层回答：**主结果按它自己声明的定义，能不能被独立算出来。**

### B. 独立口径挑战

在同口径复算完成后，红队可以提出更合理的独立定义或边界口径，检查：

- 原指标定义是否存在歧义；
- 换合理口径后结论是否反转；
- 论文是否需要限定适用范围。

最终报告必须把“数值分歧”和“口径分歧”分开记录，不允许混成一句“结果不一致”。

## REDTEAM-FROZEN-INPUT-001：随机/合成输入必须冻结

如果头条指标依赖：

- 随机种子；
- Monte Carlo 样本；
- 仿真生成数据；
- 采样场景；
- 模型内部生成的中间输入；

则必须冻结独立复算所需的输入，并记录至少：

```text
file
purpose
generation_method
seed/config
sha256
```

红队应先在同一冻结输入上做同口径复算，再决定是否需要更换随机种子或生成机制做鲁棒性挑战。否则“重新随机一次得到不同数字”不能直接证明主结果错误。

## REDTEAM-FAIL-001：没有软放行

如果红队：

- 未完成复算；
- 超时；
- 关键数据缺失；
- 多次复算仍与主结果冲突；
- 无法确认 hard constraints；

则该验收项不能因为“自动流水线还要继续”而改成 PASS。

允许其他**不依赖该失败结论**的任务继续，但当前模块保持 `FAIL / REOPEN` 或对应的 Mathematical P0 状态，直到缺口被真正消解。

## 验收报告结论只允许

- PASS；
- PASS WITH NON-MODEL PATCH；
- FAIL / REOPEN。

不要用“应该没问题”“基本对齐”“重试次数已用完所以放行”作为验收结论。

## 建议红队报告字段

```text
question/module
source_commit
input_manifest/hash
claim/metric
main_value
replicated_value
unit
declared_definition
independent_definition
relative_difference
difference_type: NUMERIC / DEFINITION / NOT_COMPARABLE
method_independence
hard_constraint_check
status
blocking_reason
evidence_files
checked_by
```
