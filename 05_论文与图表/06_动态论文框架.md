# 动态论文框架

把框架写成读者能顺着理解的求解思路，而不只是目录，不把内部验收清单搬成论文标题。每问开场与正文要求见[逐问写作 Gate](05_逐问写作与算法呈现Gate.md)，图表规则见[图表工作流](02_图表工作流.md)。

## 1. 先判断每问的成熟度

| 当前状态 | 现在可以交付 | 暂不定稿 |
|---|---|---|
| 模型未定或存在实质缺陷 | 本问输出、跨问接口、缺口与候选路线；路线有实质差异时保留少量分支 | 模型优势、完整方法论证、结果与摘要结论 |
| 路线与接口已定，结果未出 | 概述、题目化章节、公式和伪代码槽位、图表需求 | 数字、最优性、稳定性及效果判断 |
| 部分结果已冻结 | 回填有来源的部分，保留其余证据占位 | 未复核或依赖未定上游的结论 |
| 证据与模型均已确认 | 收束正文、图后解释、摘要和结论，执行写作 Gate | 超出证据范围的表述 |

按问判断，不因为 Q4 可写就认定 Q1—Q3 已成熟，也不因某一问阻塞而暂停全文。模型需要调整时，把“缺模型机制、缺验证实验、已有但漏写”分开，向技术 Owner 返回要求。文字修饰不能补上模型缺陷。

## 2. 保留已认可结构，再补缺口

用户已认可某一问的完整框架时，把它作为本轮起点。结构总览也要保留方法间的依赖、输入输出、核心求解步骤和验证位置，不能压缩成失去联系的通用标题。

新增评审意见优先落入原框架相应位置：参数依据放在参数选择与对比处，停止条件放在算法处，区域机制放在结果解释处。不因新增三条意见就把论文改成“三条审计意见”的排列。

仅当模型路线、主要输出、跨问接口或核心证据逻辑改变时，重排受影响部分；参数数值与措辞变化通常只需局部回填。解释必要的结构变化，不悄悄另起一套。

## 3. 同一写作思路，不同题目结构

每问大标题下都用一段概述承上启下，不要求同样的小标题、句式或算法。

| 求解类型 | 应讲清的关系 |
|---|---|
| 预测 | 时序/分组特征如何影响方法；如何验证；误差是否影响下游决策 |
| 调度优化 | 决策、目标和约束如何限定方案；算法怎样选择；如何与基线比较 |
| 状态/储能优化 | 状态递推如何连接时段；初末端条件如何影响结果；参数变化有什么代价 |
| 耦合迭代 | 子问题传递什么；反馈怎样改变候选；何时接受、拒绝、回退与停止 |
| 统计、评价等其他题型 | 按真实分析流程组织，不强套优化模型或“局部最优”叙事 |

本次算电训练的 Q4 可按“概述—算电关系—模型建立—交替算法—结果对比与解释”展开，这只是案例。不要把交替优化、三组参数、六个区域、50000 个任务或七年收益写成所有赛题的要求。

## 4. 细到能开始写、能提出数据要求

每个主要小节写清：本节说明什么、与前后怎样衔接；已定的方法与必要公式/真实步骤；图表放在哪里、回答什么；缺哪些结果与字段、由谁提供。

内部草稿可用 `[已确认]`、`[草稿]`、`[待证据:交付物/负责人]`、`[待决策:条件]`，正式正文删除标签。缺结果时先写比较目的，不预写“显著提升”再等数字证明。

技术请求至少说明比较对象、参数/场景、指标定义与单位、统计范围、必要字段、来源版本、图中位置和验收条件。算法日志应对应真实接受/拒绝和停止判断；不得仅发“画一张成本图”。

等待模型时完成稳定内容、图表卡、表头、文献用途和伪代码槽位。只获准搭框架时，不自行启动全量求解、改代码或补实验。

## 5. 按用户要的颗粒度交付

只要 Q4 框架，就交付该问框架，不扩张为四问重写或代码包。要求一份文件时，将框架与必要证据请求合并，把内部待办与拟入文内容分开。不强制固定文件数量；ZIP 只是容器，不表示包含代码。

交付前检查：概述是否自然引出真实方法；各节是否连接；算法是否先于效果展示；图表是否分别支撑相关指标；结果解释是否保留；模型未定部分是否标注。证据门槛沿用现有 Gate，不复制另一套。
