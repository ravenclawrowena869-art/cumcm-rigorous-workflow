# CUMCM Rigorous Workflow v2.1 设计规格

## 1. 目标

将现有 v2.0 三轨工作流升级为面向 2026 CUMCM 正赛的 v2.1：

1. 由 GPT Orchestrator 主导 FYQ 与 XXT 的建模、编程任务拆分、调度、审查与冻结；
2. CYQ 聚焦 Paper Lead，接收结构化且可直接写入论文初稿的 Paper Handoff；
3. 把 2026 华数杯 C 题三等奖评委反馈固化为正赛 Gate 与 Failure Atlas；
4. 将 Runtime Skill 从大型论文语料中拆出，形成“薄 Skill + 外置知识库 + Full Archive”；
5. 以 GitHub 仓库作为 Skill、Prompt、Workflow、Template 的 Single Source of Truth。

## 2. Authority 与事实边界

### 2.1 当前战略

- 2026 CUMCM 默认主选 C 题。
- A-Track 经验只保留可迁移的 Numerical Engineering、Objective Interpretation、Pathwise Validation、Surrogate Fidelity 与 Optimization Adequacy。
- 华数杯 C 题已结束，成绩为三等奖。后续只提炼经验，不继续追改正式参赛结果。

### 2.2 评委反馈的地位

本次华数杯评委反馈视为正式实战 Failure Evidence，优先用于修改赛时 Gate。它不被表述为“一等奖论文唯一标准”，但其指出的缺陷全部进入 Failure Atlas：

- GroupedMean 忽略时序波动；
- 经验区间没有量化下游保护效果；
- LSTF-Top-K 缺任务输入重排敏感性；
- 多目标策略缺单目标 MILP 真值锚点；
- 分区独立能源 LP 缺跨区域互联 counterfactual；
- 储能容量与功率未扫描；
- Q4 20% 调整阈值缺选取论证；
- Q4 终止条件未覆盖服务质量；
- 场景间收敛差异未分析；
- 缺末端窗口时序图与 GPU 利用率热力图；
- 每问求解部分缺本问专属伪代码或算法流程；
- Region A 不可行缺约束边界物理解释；
- 版式存在图表与正文大面积空白、跨行标题尾部仅少数字等问题。

### 3.1 GPT Orchestrator 的职责

GPT Orchestrator 不替代 FYQ 或 XXT 的长期角色，负责跨角色调度与裁决：

1. 读题与 Question Contract；
2. Atlas 相似题映射；
3. 学术原型与高质量实现检索；
4. 数据审计要求与 EDA 问题设计；
5. 主/备模型路线裁决；
6. 将建模与实现拆成 10–30 分钟可验收 Block；
7. 把 Block 动态分给 FYQ / XXT；
8. 对 Codex 任务书给出公式、输入、输出、约束、禁止项和验收；
9. 对结果做数学、工程、比赛三层 Review；
10. 追加稳健性、消融、敏感性、counterfactual 等必要实验；
11. Freeze 后生成面向 CYQ 的 Paper Handoff；
12. 总审模型、代码、数字、图表、正文的一致性。

### 3.2 FYQ

长期角色：Technical Lead。

主责：
- Coding Agent 协作；
- 数据与工程流水线；
- Git / 环境 / 测试；
- Source of Truth；
- Interface / Version / Freeze；
- clean replay；
- 联合模型技术集成。

具体某一问可同时承担数学建模 Owner，但最终数学裁决仍由 XXT 或指定 Reviewer 完成。

### 3.3 XXT

长期角色：Mathematical Lead。

主责：
- 数学抽象；
- 决策变量；
- 目标函数；
- hard constraints；
- 模型选择；
- 参数与数值合理性；
- validator specification；
- 优化充分性与边界解释。

具体某一问可承担实现 Owner，但最终工程与 Freeze 由 FYQ 或指定 Technical Reviewer 审核。

### 3.4 CYQ

长期角色：Paper Lead。

主责：
- 论文骨架；
- 摘要；
- 问题求解叙事；
- 结果解释；
- 图表叙事与排版；
- AI 使用说明；
- Final Paper。

默认不要求 CYQ 重新读代码仓库、长聊天记录或 solver 日志。CYQ 只消费冻结后的 Paper Handoff、Figure Registry、Source of Truth 和必要图表数据。

## 4. Paper Handoff v2

现有 Handoff 保留以下字段：方法、为什么、核心数学、核心结果、结果解释、正式来源、图表、论文禁区。

v2 新增五组字段。

### 4.1 本问中心逻辑

必须先给出：

- 本问真正要解决什么；
- 最大困难或约束是什么；
- 为何采取当前方法；
- 这一步给后续带来什么好处；
- 最终结论要服务哪一个下游问题或全文结论。

正文默认使用：

```text
问题 / 困难
→ 处理动作
→ 为什么这样处理
→ 带来什么收益
→ 结果证据
→ 对下一步的作用
```

### 4.2 本问专属求解流程

每问至少提供一个：

- 伪代码；或
- 算法流程图；或
- 明确的 Step 1…Step N 求解流程。

流程必须使用本题变量、约束和输入，不允许只放通用模型百科式介绍。

### 4.3 稳健性与边界

必须说明：

- 稳定范围；
- 敏感方向；
- 失效边界；
- 是否存在结构假设 counterfactual；
- 是否存在 exact / MILP / simple baseline anchor；
- 若结果只达到 FEASIBLE / COMPETITIVE，正文不得写成全局最优。

### 4.4 自然语言初稿

Owner / GPT Orchestrator 必须生成一版可直接交给 CYQ 的中文初稿，要求：

- 主谓宾清楚；
- 一句尽量只承担一个主要意思；
- 少用破折号、双引号和模板化连接词；
- 不写 Agent、日志、调试过程；
- 重点解释“为了什么”和“有什么好处”；
- 所有冻结数字、单位、定义、模型结论不得擅自变化。

### 4.5 Source of Truth

每个正式数字必须带：

- source file；
- sheet / row / column 或结构化 key；
- freeze version；
- 生成脚本；
- 如适用，图表数据源。

## 5. 评委反馈 Gate

### 5.1 Forecasting Gate

任何纯均值预测只能作为 baseline。

若数据存在显著时序结构，至少加入一个 time-aware challenger，并比较：

- MAE / RMSE；
- 极端窗口误差；
- 突变时段误差；
- 下游调度成本 / 可行率 / 风险。

预测区间若进入调度，必须量化它对下游的保护效果。

### 5.2 Heuristic Order Sensitivity Gate

任何顺序相关启发式都必须做输入顺序扰动：

- 原顺序；
- 多个随机 permutation；
- 至少一个反向或 worst-like ordering（可构造时）。

报告：objective best / median / worst / std、feasibility rate、关键 SLA 波动。

### 5.3 Exact Anchor Gate

启发式、多目标规则或分解方法，只要存在可解的小规模 exact formulation，就应提供 MILP / CP-SAT / exhaustive / relaxed anchor。

至少报告：

```text
heuristic_gap = (J_heuristic - J_anchor) / |J_anchor|
```

若 exact 只能覆盖缩小实例，必须明确实例规模和适用边界。

### 5.4 Structural Assumption Counterfactual Gate

关键结构假设必须至少挑一个做对照。

例：
- 区域电力独立 vs 允许跨区互济；
- 固定 PUE vs 有限变化；
- 不允许迁移 vs 允许迁移；
- 硬时窗 vs 软惩罚。

目的不是增加模型数量，而是量化关键假设对结论的影响。

### 5.5 Storage Parameter Surface Gate

储能题默认扫描：

- Energy capacity；
- Charge / discharge power；

优先二维参数面而非单参数 ±10%。输出：

- 成本 / 碳 / 削峰 / 新能源利用率；
- 边际收益；
- 饱和区；
- 失效区。

### 5.6 Iterative Algorithm Gate

任何经验阈值，如 20% 调整上限，必须做参数扫描或对照论证。

终止条件至少覆盖：

- 主目标改善；
- 关键约束；
- 服务质量，例如时延、等待时长、SLA。

多场景需报告迭代次数与收敛轨迹差异。

### 5.7 Infeasibility Diagnosis Gate

出现 infeasible 时，不允许只报告 solver status。

必须定位：

- 哪一组约束最先压缩可行域；
- 哪个资源达到边界；
- 最小 relax 量；
- 该边界的业务/物理含义。

## 6. Figure Registry v2

图表分为：

1. 结果图；
2. 机制图；
3. 诊断图；
4. 稳健性图。

新增默认候选：

- 末端窗口放大时序图；
- GPU 利用率专题热力图；
- 迭代收敛曲线；
- 参数二维响应面；
- 约束边界 / 可行域诊断；
- heuristic permutation 分布图。

图表入文前检查：

- 正文首次引用与图位置合理；
- 不造成上一页大面积空白；
- 标题尽量不出现只剩 2–3 个字的跨行尾巴；
- 单位、样本量、时间范围、场景在图注或正文交代。

## 7. AI 使用说明 v2

继续采用：

```text
聊天记录 → 知识库 → 团队框架 → 人工重写
```

同时维护 AI Use Ledger：

- 时间；
- 工具 / 版本；
- 使用环节；
- Prompt 摘要；
- AI 回复摘要；
- 人工核验；
- 团队决定；
- 实际采纳；
- 人工修改；
- 进入论文位置。

AI 使用说明必须如实描述实际参与深度，不以规避检测为目标。

## 8. Runtime Lite Skill 架构

### 8.1 原则

Runtime Skill 只携带执行必需的：

- SKILL.md；
- references/*.md；
- templates/*；
- tests / validation；
- corpus manifest；
- source index；
- hashes / provenance。

不把大体积优秀论文 PDF / PNG 直接打进日常 Skill。

### 8.2 Full Archive

Full Archive 保留：

- 原始优秀论文；
- 页面截图；
- 完整 corpus；
- provenance。

用于备份、迁移、灾难恢复和离线重建。

### 8.3 外置知识源

比赛时全文证据优先从：

1. 当前 Project Files；
2. GitHub repo 的轻量 references；
3. Full Archive；
4. 外部学术检索；

按任务需要读取，避免把全部原文注入 Runtime Skill。

## 9. GitHub Source of Truth

仓库作为唯一正式 Skill / Workflow 源。

必须落盘：

```text
/skills
/prompts
/interfaces
/tests
/docs
/templates
/project_state.yaml
```

任何关键规则不得只存在于 ChatGPT、Codex、Claude 或临时聊天中。

### 9.1 分支与合并

- 不直接修改 main；
- 每次 Skill / Workflow 更新创建 feature branch；
- 修改完成后提交 PR；
- PR 描述必须列出 Gate 变化、行为变化、兼容性和验证结果。

## 10. 兼容性

v2.1 不废弃 v2.0 的三轨并行、Owner 动态分配、Interface First、Mock 解耦、Freeze、Source of Truth 和 clean replay。

v2.1 的主要变化是：

- 新增 GPT Orchestrator；
- 强化 Paper Handoff；
- 增加评委反馈 Gate；
- 增加 Figure Registry v2；
- Runtime Skill 与原论文 corpus 解耦。

## 11. 验收标准

v2.1 实施完成后应满足：

1. README 明确 GPT Orchestrator 与三人长期角色关系；
2. 协作目录包含 Orchestrator 分派规则与 Paper Handoff v2；
3. 建模/验收目录包含评委反馈 Gate；
4. 论文目录包含目的—收益—证据写法、本问专属求解流程和稳健性要求；
5. AI 目录包含 AI Use Ledger 与“聊天记录—知识库—框架—人工重写”；
6. Skill 目录形成 Runtime Lite 结构，不含大体积 PDF/PNG；
7. Full Archive 策略有明确文档和 manifest；
8. 模板可直接生成任务单、Paper Handoff、Robustness Plan、AI Use Ledger；
9. 至少有静态验证脚本检查关键文件、必填字段和禁止项；
10. 所有改动在 feature branch，通过 PR 交付。
